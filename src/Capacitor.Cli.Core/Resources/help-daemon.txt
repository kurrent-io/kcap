kcap daemon — Manage the daemon process

Usage: kcap daemon <subcommand>

Subcommands:
  start [-d]              Start the daemon (foreground, or -d for background)
  stop [--name N] [--yes] [--keep-agents]
                          Stop a running daemon and end its hosted agents
                          (prompts on multi unless --yes)
  restart [--name N]      Restart the daemon now; its hosted agents are stopped
                          and resumed (--when-idle queues; --force skips the
                          flow-round wait)
  status [--name N]       Show daemon status, incl. the running daemon's
                          version (lists all when --name omitted)
  logs                    Show recent daemon log output
  doctor [--clean]        Diagnose lock-file state, optionally clean stale entries
  service <action>        Manage the OS service (launchd/systemd/Scheduled Task)
  shim <action>           Manage the command-line tool (kcap on your terminal PATH)
  consent <verb>          Manage the launch-consent policy (see "Consent" below)
  steering <on|off>       Turn steering of this profile's terminal Claude Code
                          sessions on or off (see "Steering" below)
  steering-socket         Print the daemon's steering socket, or nothing

Options for start:
  --name <name>           Daemon name (defaults to OS username)
  --server-url <url>      Server URL
  --max-agents <n>        Max concurrent hosted coding agents (default: 5; 0 = unlimited)
  --log-file <path>       Log to file instead of console
  --log-level <level>     Log verbosity: trace|debug|information|warning|error|
                          critical|none (default: information). Also settable via
                          KCAP_DAEMON_LOG_LEVEL; the flag wins when both are set.
                          Use debug for transport diagnostics (e.g. DaemonPing RTT).
  -d, --detach            Run in background (logs to file automatically)

Options for stop:
  --name <name>           Stop just the named daemon. Without it, all daemons
                          are listed and the command asks for confirmation
                          before stopping them (unless --yes is passed).
  --yes, -y               Unattended mode: stop all running daemons without
                          prompting. Useful in cleanup scripts.
  --keep-agents           Stop the hosted agents so the next start relaunches them
                          on their saved sessions; a turn in progress is cut off.
  --direct                Windows only: ask the daemon itself even when a service
                          manages it. The Windows service uses it for its own
                          graceful stop; to stop a supervised daemon, use
                          `daemon service stop`.

A daemon that a service supervises (launchd, systemd, or on Windows kcap-service
or a Scheduled Task) is not stopped, since the service would restart it: stop
exits 1 and prints the `kcap daemon service stop --name N` command to use.

Options for restart:
  (none)                  Restart now. Interactive agents and Claude flow
                          reviewers are stopped and resumed on the new daemon.
                          Refused while an eval, a launch or a flow
                          participant's round is in progress.
  --when-idle             Queue the restart; it applies once the daemon hosts no
                          agents at all and no eval or launch is in progress.
                          Returns immediately.
  --force                 Restart without waiting for a flow round: a flow
                          participant mid-round is resumed with its round (a
                          Claude reviewer), parked (Codex) or ended. An eval or a
                          launch in progress still holds the restart.

Updating: after `kcap update`, a running daemon detects the new binary and
restarts itself, stopping its hosted agents and resuming them on the new
version unless daemon.auto_resume is false. It waits until no eval, launch
or flow round is in progress and every interactive agent is waiting on
input, with no Claude Code background subagent running, so a daemon with
nothing in progress restarts at once. Turns, Claude Code background
subagents and flow rounds hold it for at most
KCAP_RESTART_TURN_WAIT_SECONDS, then are cut off; an eval or a launch
holds it past that limit. `kcap daemon status` reports
the running daemon's version plus any pending restart, so you can confirm
a self-update took effect. A daemon started in a terminal restarts only
by hand. On Windows a daemon started on a release that did not watch for
updates there needs `kcap daemon restart` once.

Resume after a restart: `kcap agent ls` shows each agent's state (running,
resuming, interrupted), and `kcap agent resume <id>` retries an interrupted one.
`kcap config set daemon.auto_resume false` leaves agents interrupted instead of
resuming them at start. Tuning, read from the environment:
  KCAP_RESTART_TURN_WAIT_SECONDS  Turn-boundary wait for a self-update (default 300)
  KCAP_RESUME_MAX_AGE_SECONDS     Oldest agent a starting daemon resumes (default 86400; 0 for no bound)
  KCAP_RESUME_CONCURRENCY         Agents resumed at once (default 2)
  KCAP_RESUME_READINESS_SECONDS   How long a resumed agent must stay up (default 10)
  KCAP_ATTACH_RECONNECT_SECONDS   How long `kcap agent attach` waits for its agent
                                  to come back (default 90)

Options for doctor:
  --clean                 Remove stale entries (lock files whose holder is
                          gone). Held entries are never touched. Without
                          --clean, doctor reports state without modifying.

Subcommands for service (per-user; restarts the daemon if it crashes, starts it at login):
  install [--name N] [--profile P] [--max-agents N] [--no-start] [--replace] [--verify] [--retire ID]
                          Register the daemon as an OS service and start it.
                          Pins the profile via KCAP_PROFILE and captures PATH so
                          claude/codex resolve as they do in your shell. --verify
                          polls readiness (hello), version, and ownership (job
                          pid) before
                          exiting 0, rolling back (uninstalling the unit) and
                          exiting with a coded stderr token (e.g.
                          verify_hello_validation) if that never happens within
                          the poll budget. --replace (requires --verify) takes
                          over an existing label/unit — clears a foreign/loaded
                          label, stops a validated live owner, then installs.
                          --retire ID (requires --replace --verify) also removes
                          the unit ID in the same transaction — the one a rename
                          leaves behind. Refused unless that unit is pinned to
                          the same profile; a live daemon under the NEW name is
                          contended, never taken over.
                          --no-start cannot be combined with --verify (verify
                          proves the STARTED daemon is ready).
                          Refused, changing nothing, from inside an agent that
                          the daemon it would stop or retire hosts: stopping
                          that daemon would end the command partway. Run it
                          from a terminal the daemon does not host.
  install --system [...]  Windows: first install or update the machine's
                          kcap-service (one administrator prompt), then hand
                          this daemon to it. Needs the desktop app's install,
                          which carries kcap-service.exe. A declined prompt
                          exits 1223 and changes nothing. A local server its
                          Scheduled Task runs moves to kcap-service too.
  uninstall [--name N]    Stop and remove the service unit.
  uninstall --system      Windows: move the local server and this daemon back
                          to their Scheduled Tasks, then remove the machine's
                          kcap-service (one administrator prompt). The daemon
                          stops with its agents kept for its task's daemon to
                          resume; the task starts it when the service was
                          running it. A move that fails leaves kcap-service
                          installed; a declined prompt leaves both on their
                          tasks.
                          Moving a running local server either way restarts
                          it: the command waits until it is ready again, says
                          how long it was down, and exits 1 when it does not
                          come back.
  uninstall --under DIR   Stop and remove every unit whose daemon binary is
                          inside DIR, and no other. The desktop app's
                          uninstaller runs this for its own folder.
  repoint --from DIR      Windows: point every Scheduled Task whose daemon
                          binary is inside DIR at this install's daemon,
                          keeping the rest of its task. A running daemon
                          restarts with its agents kept; a busy one stays on
                          the old binary and the command exits 1. The desktop
                          app runs this before it removes a Kurrent Capacitor
                          install.
  start [--name N] [--verify]
                          Start the installed service now. --verify polls
                          readiness (hello) and ownership (job pid) before exiting 0,
                          rolling back and exiting with a coded stderr token
                          (e.g. verify_readiness_timeout) if the service never
                          comes up within the poll budget.
  stop [--name N] [--keep-agents]
                          Stop the running service (unloads/deregisters it with
                          the OS supervisor; stays installed — returns at next
                          login or `service start`). Ends its hosted agents;
                          --keep-agents stops them so the next start relaunches
                          them on their saved sessions (a turn in progress is
                          cut off). The desktop app starts a stopped daemon
                          service when it opens, not while it is open. Plain
                          start (without --verify) and stop wait up to a
                          minute for another operation on the service to
                          finish.
  ensure [--name N] [--profile P] [--json]
                          Flow-driven ladder: from a fresh status read, install
                          when there is no unit (baking the born-prompt consent
                          directive) or start when the unit is present but
                          stopped; "already enabled" when the daemon is running
                          (on launchd only when the service job owns the
                          validated daemon pid). On macOS/launchd both arms run
                          the verified transaction, so a gate refusal exits with
                          the coded verify exit plus start_gate_reason=, mapped
                          to recovery_surface=takeover|reinstall|attention —
                          never guessed from prose; coded viability/refusal
                          reasons route likewise (package_inconsistent →
                          reinstall, boot refusals → storage/takeover), and
                          refused launchd transactions report verified:true.
                          Windows/Linux degrade to plain install/start (no
                          gates; --json reports verified:false). macOS requires
                          a resolvable profile (no_profile_configured refusal
                          otherwise). Ambiguous states (unknown probe, active
                          transaction, orphan label — running included — stale
                          marker) fail closed to attention with a coded reason
                          — never mutated into.
  status [--name N] [--json]
                          Show installed / running state. Under kcap-service it
                          also says whether the service started or adopted the
                          daemon, and whether it runs your local server too.
                          --json emits a machine-readable snapshot
                          (service/job/daemon pids, binary paths,
                          transaction-marker state) and exits non-zero if the
                          underlying service state can't be determined.
  refresh [--force]       Bring installed units up to this version. A reload
                          stops the daemon with its hosted agents kept, and the
                          reloaded daemon resumes them; --force reloads the
                          named daemon and prints refresh_outcome=<token> on
                          stderr; launchd only.

Subcommands for shim (the command-line tool — kcap on your terminal PATH):
  ensure [--json]         Probe a new terminal's PATH. If kcap already
                          resolves, report already_on_path and exit 0. If it
                          is absent, link kcap to this CLI in the first PATH
                          folder you can write to, else in ~/.local/bin
                          (macOS also adds that folder to PATH in your shell
                          profile), or add its folder to your user PATH
                          (Windows). No admin password is ever asked for. Then
                          re-probe so success is never reported on the change
                          alone. Every ambiguous row fails closed with a coded
                          reason: an unknown probe (probe_unknown), a
                          different filesystem entry at the destination
                          (conflict), or a platform with no installer
                          (unsupported_platform) — nothing is ever guessed or
                          overwritten. --json emits the outcome + coded reason
                          the flow keys off (e.g. installed, refused).
                          Exit 0 only when the terminal now resolves kcap.

Consent:
  Every SERVER-driven launch (a coding agent, PR review, or review-flow
  participant started from the dashboard) is checked against a daemon-owned
  launch-consent policy before it runs. Launches from the daemon's own local
  socket (`kcap agent start`) are always the owner's and never consult this
  policy. The daemon owner is ALWAYS allowed, regardless of the policy below
  — this built-in bypass cannot be turned off. For everyone else, rules are
  checked in order and the FIRST MATCH WINS; a request that matches no rule
  falls through to the policy's default. A denial surfaces to the server (and
  the requester) as the coded reason `launch_denied_by_owner`.

  kcap daemon consent show                       Print the current default,
                                                   prompt timeout, and every
                                                   rule with its index
  kcap daemon consent set-default <allow|deny|prompt>
                                                   Set the fallback verdict
                                                   for a request no rule
                                                   matches:
                                                     allow  — let it through
                                                              (upgrade-safe;
                                                              every daemon
                                                              starts here)
                                                     deny   — reject it
                                                     prompt — ask the daemon
                                                              owner, and deny
                                                              on timeout / no
                                                              approval UI
                                                              attached
  kcap daemon consent allow [--requester U] [--kind agent|review|review-flow]
                             [--repo PATH] [--vendor V]
                                                   Append an "allow" rule
  kcap daemon consent deny  [--requester U] [--kind agent|review|review-flow]
                             [--repo PATH] [--vendor V]
                                                   Append a "deny" rule
  kcap daemon consent remove <index>              Remove the rule at the
                                                   index printed by `show`
  kcap daemon consent log [-n N]                  Tail N lines (default 20)
                                                   of consent-decisions.jsonl
                                                   — a direct file read, so
                                                   it works with the daemon
                                                   stopped

  `show`/`set-default`/`allow`/`deny`/`remove` mutate the policy over the
  daemon's local socket and require a running daemon. `allow`/`deny` require
  at least one of --requester/--kind/--repo/--vendor — an omitted field is a
  wildcard (matches anything), so a flagless "allow" would be a permanent
  no-op, and a flagless "deny" is already expressible as `set-default deny`.
  --repo accepts an exact path or a "/prefix/*" glob. All six verbs take
  --name <n> like the rest of `kcap daemon`.

Steering:
  Steering lets you send messages from the kcap web and mobile apps into
  Claude Code sessions running in your own terminal, through the
  kcap-steering Claude Code plugin, which talks to the daemon. It is off by
  default; `kcap setup` asks whether to turn it on once kcap's Claude Code
  plugin is installed and the daemon service is up. The switch belongs to one
  daemon, so each profile has its own, and turning it on for one profile
  leaves the other's sessions closed.

  kcap daemon steering on|off   Turn it on or off for the current profile's
                                daemon, which must be running. The daemon
                                saves the switch and opens or closes its
                                steering socket at once, with no restart.
  kcap daemon steering-socket   Print the steering socket's path, and nothing
                                else, while steering is on and the daemon is
                                running; otherwise print nothing. Exits 0
                                either way.

  The first `steering on` installs and enables the kcap-steering plugin
  wherever kcap's own Claude Code plugin is installed (the user settings, and
  each Claude config dir `kcap accounts` records), once per settings file
  rather than per profile: if you later disable or uninstall it in Claude
  Code, turning steering on again leaves it that way and says so. Sessions
  started after the install load it. A session started while steering was
  off, or while the daemon was down, is steered from its next /clear, resume
  or restart, and a Claude config dir added later with `kcap accounts add`
  gets the plugin at the next `steering on`. Where kcap's plugin isn't
  installed, nothing is written; if it is installed nowhere, steering still
  turns on and the command says so and exits 1: run `kcap plugin install`,
  then `steering on` again. `steering off` leaves the steering plugin installed,
  doing nothing while the switch is off. If a settings file can't be written,
  steering still turns on and the command says why and exits 1; install the
  plugin by hand with `claude plugin install kcap-steering@kcap`, or fix the
  cause and run `steering on` again.

  If a message from the web or mobile app keeps waiting while the terminal
  sits idle, type at the terminal, or run /clear: the plugin hands a message
  over only between turns, and it can miss the end of one. /clear starts a
  new conversation and drops the waiting message, so send it again
  afterwards.

  Steering needs a kcap server that takes steered sessions. The daemon asks
  its server once per connection, before it registers any; against one that
  doesn't, it steers nothing, and the plugin asks again every ten seconds, so
  a server upgrade is picked up without a restart.

  The socket is owner-only, in a directory only you can enter, and that is
  its only authentication: no token ever reaches a session. Both verbs take
  --name <n>. Steering isn't offered on Windows yet: `steering on` refuses
  there, `steering-socket` prints nothing, and setup doesn't ask.

Notes:
  Each daemon holds an exclusive flock on ~/.config/kcap/daemons/<name>.lock
  for its entire lifetime. The kernel releases the lock automatically on
  process exit (including SIGKILL or power-off), so stale lock files on disk
  are never a blocker — only a live process holding the kernel-level lock
  can prevent another daemon from acquiring the same name.

  Two daemons with different --name values can run side-by-side. Two daemons
  under the same name on the same machine collide on the flock and the
  second one exits with code 2. If they somehow both connect to the server
  anyway, the server-side check rejects the second one with exit code 3.
